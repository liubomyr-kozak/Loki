# Backend config & core module map

This page indexes the file-level responsibilities of the backend's config
subsystem (`backend/config/*.ts`), the plugin-runtime indirection layer
(`backend/core/*.ts`), and the root type/error modules
(`backend/config.types.ts`, `backend/runtime.types.ts`, `backend/types.ts`,
`backend/errors.ts`, `backend/plugin.types.ts`). It is a coverage map, not a
narrative — for the *why* behind the read/write asymmetry, the zod
assertion pattern, and several individual functions' rationale, see
[Config read/write contract](../entities/config-read-write-contract.md),
which this page cross-links into rather than duplicates.

## `backend/config/` — load, validate, mutate, and side-file storage

| File | Responsibility | Key exports | Contract / invariant | Consumers |
|---|---|---|---|---|
| `loadConfig.ts` | Read config off disk (JSON or limited YAML), synthesize + persist a default on first boot, normalize `global.sessionsDir`/`stateFile`/`apps.*.surface` defaults, then validate via `ConfigSchema`. | `loadConfig(filePath)` | Only auto-creates `.json` paths (not YAML); writes the first-boot default via temp-file-then-`renameSync` so a crash never leaves a truncated config. Relative `stateFile`/`sessionsDir` are resolved against the **config file's own folder** (never `process.cwd()`), and written to disk as relative so the config stays portable. See contract page §"config folder is the anchor". | `configState.ts` (`initConfig`/`reloadConfig`) |
| `schema.ts` | Single source of zod schemas for every config shape, both read-path (lenient, `.passthrough()`) and write-path (`AppConfigWriteSchema`, stricter). Also carries compile-time `_assert<Exact/AssignableTo<...>>()` checks tying each schema to its hand-written TS interface. | `EnvFilterConfigSchema`, `AppSurfaceSchema`, `AppConfigSchema`, `WorkspaceConfigSchema`, `GlobalConfigSchema`, `ConfigSchema`, `SurfaceSchema`, `PluginMetaSchema`, `CatalogEntrySchema`, `ControlDescriptorSchema`, `ControlGroupDescriptorSchema`, `PluginDescriptorSchema`, `AppConfigWriteSchema` | `EnvFilterConfigSchema` (`{ useGlobal, filterRegex? }`) is the per-app environment-filter override; environments themselves are derived from `package.json` scripts rather than declared. Read-path object schemas `.passthrough()` (preserve unknown/provider keys); `PluginMetaSchema`/`ControlDescriptorSchema` `.strip()` (internal-only shapes). `AppConfigWriteSchema` is a **separate** stricter object from `AppConfigSchema`, not a mode toggle. Full rationale in the contract page's "R1" and "Compile-time type-vs-schema assertions" sections. | `loadConfig.ts`, `configValidation.ts`, `appConfigOps.ts`, `globalConfigOps.ts` |
| `configValidation.ts` | Write-path validation entry points: key sanitization and thin wrappers around the write-path zod schemas. | `sanitizeKey(s)`, `validateIconShape(icon)`, `validateAppConfig(app)` | `sanitizeKey` enforces the `^[a-z0-9][a-z0-9-]*$` key-name regex used for app keys; `validateAppConfig` parses against `AppConfigWriteSchema` and throws on failure (caller — routes — turns that into a 4xx). | Re-exported via `configStore.ts`; used by `appConfigOps.ts` (`validateIconShape`) and routes |
| `configMutation.ts` | Generic "read whole config file as JSON, mutate one top-level section/array in place, write back" primitive, specialized per section/array. | `mutateConfigFile(configFile, fn)` (section `apps`), `mutateGlobalConfigFile(configFile, fn)` (section `global`), `mutateGroupOrderFile(configFile, fn)` / `mutatePluginsFile(configFile, fn)` / `mutateDisabledPluginsFile(configFile, fn)` (top-level arrays `groupOrder`/`plugins`/`disabledPlugins`) — all thin wrappers over the internal `mutateConfigSection`/`mutateTopLevelArrayFile` | Every write goes through a shared `writeJsonAtomic(absPath, json)` helper (unique-per-call tmp path + `renameSync`) — `mutateConfigSection` (object-shaped sections: `apps`/`global`) used to write via a direct `writeFileSync` and was hardened to reuse this same helper, matching what the array-shaped mutators already had; a crash mid-write now leaves only an orphaned `.tmp` file rather than a truncated `orchestrator.json` for **any** of these mutators. All of them are additionally serialized per resolved absolute path through an in-process `withFileLock`/`fileLocks` promise chain (`configMutation.ts:19-39`) — a plain read→mutate→write with no lock previously let two overlapping calls against the same file (e.g. an install racing an activate) read the same pre-mutation state and have one silently clobber the other; the lock is single-process only, no cross-process locking, and one turn's rejection is swallowed in the tracked tail so a failed mutation never wedges the queue for later callers. See contract page's `configState.ts` section (updated) for the full before/after. | Re-exported via `configStore.ts`; used by config/app/plugin routes |
| `configState.ts` | The **sole** synchronous owner of the in-memory `Config` singleton. | `getConfigFile()`, `getConfig()`, `reloadConfig()`, `initConfig()` | Single writer (`reloadConfig`), single guarded reader (`getConfig`); replaced a scattered `let config` reassigned in 9 places. `initConfig()` exits the process (`process.exit(1)`) if the very first load fails. Kept synchronous deliberately — see contract page's `configState.ts` section. | `backend/index.ts`/`server.ts` at boot; virtually every route/op module that needs current config |
| `configStore.ts` | Barrel re-export tying `configValidation.ts` + `configMutation.ts` + `appConfigOps.ts` + `globalConfigOps.ts` into one import surface. | re-exports: `sanitizeKey`, `validateAppConfig`, `mutateConfigFile`, `mutateGlobalConfigFile`, `mutateGroupOrderFile`, `mutatePluginsFile`, `mutateDisabledPluginsFile`, `mutateWholeConfigFile`, `addApp`, `patchApp`, `removeApp`, `getGlobalConfigKeys`, `patchGlobalConfig` | No logic of its own — exists so callers do `import { patchApp } from './config/configStore'` instead of reaching into five separate files. | Routes (`routes/config.ts`, `routes/apps.ts`, etc.) |
| `appConfigOps.ts` | In-memory mutators for a single app's config object: create, patch fields, remove. Environments are **not** among them — they are derived from the repo's `package.json` scripts at runtime, never declared per app (see [Config read/write contract](../entities/config-read-write-contract.md) §"environments are derived, not declared"). | `addApp(apps, key, appConfig)`, `patchApp(apps, name, patch)`, `removeApp(apps, name)` | `patchApp` is **hand-rolled per field** (not zod) for `label`/`repoPath`/`repoUrl`/`appUrl`/`dependsOn`/`surface`/`icon`/`groups`/`plugins`, with an empty-string/empty-array convention meaning "delete this optional field." This is a known drift risk versus the zod write schemas — see contract page's "Known drift risk: patch paths are hand-rolled" section. | Routes via `configStore.ts` barrel |
| `globalConfigOps.ts` | Computes the allowlist of patchable `global.*` keys (core keys + every registered session provider's own settings keys) and applies a validated patch to the in-memory `GlobalConfig`. | `getGlobalConfigKeys()`, `patchGlobalConfig(global, patch)` | Both are **functions called per request**, not module-load consts, because providers self-register via side-effecting imports; `getGlobalConfigKeys` throws if a provider's setting key collides with a base key. `patchGlobalConfig`'s empty-string/`null` value deletes the key. See contract page's "`patchGlobalConfig` and the provider-key allowlist" section. | `routes/config.ts` (`POST /api/config/global/*`), re-exported via `configStore.ts` |
| `jsonStore.ts` | Shared factory collapsing "derive path → guarded read with fallback/coerce → mkdir-then-write" into one `JsonFileIO<T>` shape, in two flavors. | `jsonSidecarStore<T>(config, spec)` (config-relative sidecar files, default-on-parse-error), `jsonPathStore<T>(file, spec)` (explicit-path files, throw-on-parse-error by default) | Sidecar flavor resolves its path via `statePaths.ts`'s `sidecarPath`; both flavors support an optional `coerce(raw, fallback)` hook for legacy-shape migration on read (see `process/selections.ts` in the contract page). See contract page's "`jsonStore.ts`" section. | `favoritesStore.ts`, `plugins/pluginState.ts`, `process/selections.ts`, `git/gitStashStore.ts`, `process/registry.ts` |
| `favoritesStore.ts` | Read/write the `favorites.json` sidecar (favorited app names + custom app order). | `readFavorites(config)`, `writeFavorites(config, favorites)`, `readOrder(config)`, `writeOrder(config, order)` | Built on `jsonSidecarStore`; both fields default to `[]` if missing/non-array. Not schema-validated beyond the array-of-string coercion done inline. | `routes` handling favorites/order endpoints |
| `configLocation.ts` | Single source of truth for **where** the config lives and what it is called — the folder every other path in this cluster is anchored to. | `STATE_DIR_NAME` (`state`), `CONFIG_FILE_NAME` (`loki-config.json`), `defaultConfigFile(baseDir?)`, `resolveConfigFile()`, `configFolder(configFile)` | The invariant is `stateDir := dirname(configFile)`: config, `state.json`, every sidecar and the session-output dir share one folder. Dev → `<repo>/state/`; packaged → Tauri's already-private `app_config_dir()`, with **no** `state` nesting added (which is why a nested `state/state/` must never appear). `resolveConfigFile()` prefers `CONFIG_FILE` (the packaged shell passes an absolute path) and otherwise returns the dev default. Deliberately carries **no** legacy filename constants — older layouts are not read at all. | `configState.ts`, `statePaths.ts`, `scan.ts`, `apps/providerRegistry.ts`, `backend/index.ts` |
| `statePaths.ts` | Single formula for deriving the state file path and any sidecar file's path relative to it. | `DEFAULT_STATE_FILE`, `resolveStateFile(config)`, `sidecarPath(config, name)` | `resolveStateFile` falls back to `DEFAULT_STATE_FILE` (an **absolute** path computed from the default config folder) when `config.global.stateFile` is unset; `sidecarPath` joins `name` under that file's **directory**, not its own path — so every sidecar (favorites, plugin state, stash map, registry, selections) lives next to `state.json`. | `jsonStore.ts`, `backend/index.ts`, several `backend/plugins/*` and `backend/apps/*` modules (registry/session/lifecycle/template-context), `routes/apps.ts`, `routes/plugins.ts` |
| `yamlParser.ts` | Minimal indentation-based YAML-subset parser used only for `.yaml`/`.yml` config files. | `parseSimpleYaml(text)` | Handles nested objects/lists via indentation only — no anchors, references, multi-line strings, or complex scalars; any value containing a colon must be quoted. Deliberately a scope-limited convenience, not a general parser — see contract page's "`parseSimpleYaml`" section. | `loadConfig.ts` |
| `scan.ts` | Runtime/environment detection: resolves the session-output directory, detects installed components (tmux/Node/shell), and scans a project directory's `package.json` for runnable scripts; also looks up which configured app owns a given repo path. | `resolveSessionsDir(configFilePath, sessionsDir)`, `detectRuntime(configFilePath?, config?)`, `detectComponents(_configFile?)`, `detectShellCandidates()`, `scanProject(dirPath, config)`, `findAppByRepoPath(config, dirPath)` | `resolveSessionsDir` is the **one shared formula** used by both `detectRuntime()` (what Settings UI displays) and the app manager's provider priming (where session output is actually written) — see contract page's "`resolveSessionsDir`" section. `detectComponents`'s tmux check reuses `tmuxProvider`'s cached `availability()` rather than forking a fresh `tmux -V`. `scanProject` caps `package.json` size at `MAX_PACKAGE_JSON_SIZE` (256 KiB) and classifies scripts as `isRunLike` via a `dev/start/serve/watch` name regex. | `apps/providerRegistry.ts`, `routes/config.ts` |

## `backend/core/` — plugin-runtime indirection to avoid a cycle

| File | Responsibility | Key exports | Contract / invariant | Consumers |
|---|---|---|---|---|
| `appOps.ts` | Defines the `AppOps` interface (start/stop/restart/status/tmux-run) that the real app manager implements, plus a registration/lookup indirection so plugin code can call into app lifecycle without importing `apps/appManager.ts` directly. | `AppOps` (interface), `registerAppOps(ops)`, `getAppOps()` | `getAppOps()` must only be resolved lazily inside request/lifecycle-time closures, **never at module-eval time** — the real implementation is registered by `apps/appManager.ts` at its own module load, and this indirection exists specifically to break an import cycle between the plugin runtime/lifecycle modules and the app manager. Calling `getAppOps()` before registration throws with a message pointing at `apps/appManager`. | `backend/plugins/pluginDescriptorService.ts`, `backend/plugins/runtime.ts`, `backend/plugins/lifecycle.ts` (callers); `backend/apps/appManager.ts` (the registrant) |

## Root type/error modules

| File | Responsibility | Key exports | Contract / invariant | Consumers |
|---|---|---|---|---|
| `config.types.ts` | Hand-written interfaces for the on-disk/in-memory config shape — the types every `schema.ts` zod schema is asserted against. | `AppConfig`, `WorkspaceConfig`, `AttachBehavior`, `GlobalConfig`, `Config`, `Surface`, `APP_SURFACES`, `AppSurface` | `AppSurface` is derived from the broader `Surface` union via `APP_SURFACES = [...] as const satisfies readonly Surface[]` rather than hand-duplicated, so it can't drift from `Surface` (`'menu'`/`'header'` are plugin-only placements an app can never use). `AppConfig.icon` is deliberately kept a separate concept from `ControlDescriptor.icon` — see contract page's "App fields" section for both. | Re-exported through `backend/types.ts`; consumed by `schema.ts`'s `_assert<...>` checks and every module operating on `Config`/`AppConfig` |
| `runtime.types.ts` | Hand-written interfaces for runtime/process state — selections, process registry entries, and the computed `AppStatus` shape returned to the frontend. | `AppSelection`, `ProcessState`, `ProcessRegistry`, `StatusContext`, `AppRunState`, `AppStatus` | `AppStatus.hasStashForBranch` is a raw sidecar-JSON read (no git spawn) and can go stale if the stash was dropped outside the orchestrator — callers must not treat it as a live git-truth check; see contract page's "Staleness caveat" section. | Re-exported through `backend/types.ts`; consumed by `core/appOps.ts`'s `AppOps` interface, status-computation code, routes |
| `types.ts` | Barrel re-export merging `config.types.ts` + `runtime.types.ts` + `plugin.types.ts` into the one `../types` import path used throughout the backend. | re-exports all of the above (types only, plus the `APP_SURFACES` value) | No logic — a single stable import surface so internal modules don't need to know which of the three source files a given type lives in. | Nearly every backend module (`import { Config, AppConfig, ... } from '../types'` / `'./types'`) |
| `errors.ts` | One shared helper for turning an unknown thrown value into a human-readable string. | `errorMessage(err)` | Mirrors the legacy `(err as any).message ?? err` fallback exactly: returns `err.message` for real `Error`s, falls back to a `.message` string property on any object, else `String(err)`. | `configState.ts` (`initConfig`'s catch), `scan.ts` (`scanProject`'s catch), and error-handling call sites across routes/ops |
| `plugin.types.ts` | Hand-written interfaces for the whole plugin contract: control descriptors, plugin metadata, the host API surface exposed to plugin code, plugin execution context, lifecycle hooks, and installed/toggle state shapes. | `ToggleDescriptor`, `ButtonDescriptor`, `ControlDescriptor`, `PluginMeta`, `HostAPI`, `AppPluginContext`, `GlobalPluginContext`, `PluginContext`, `PluginLifecycleInfo`, `PluginModule`, `InstalledPlugin`, `PluginState`, `ToggleState`, `TemplateContext` | `ControlDescriptor` is a discriminated union (`ToggleDescriptor | ButtonDescriptor`) on `action`; `PluginContext` is similarly discriminated on `scope` (`'app'` vs `'global'`), with `AppPluginContext` requiring `app`/`status`/`appSurface` and `GlobalPluginContext` explicitly typing them `undefined` rather than omitting them, so a `scope`-narrowed context can't accidentally read stale app-scoped fields. `HostAPI` is the entire capability surface a plugin module is allowed to call (config read, app start/stop/restart/status, run a process, open a URL, read/write a file, read/write plugin state, render a template) — nothing else is reachable from plugin code by contract. | Re-exported through `backend/types.ts`; consumed by `schema.ts` (`PluginMetaSchema`/`ControlDescriptorSchema` assertions), `backend/plugins/*` (descriptor service, runtime, lifecycle), plugin authors' own modules |
